# Stable 3.0 scaling evaluation (2026-08-10)

This evaluation measures the stable-tag candidate at commit `55484e8` plus the release-gate harness
and API/documentation changes in TASK-039. It is reproducible with the commands in
[`benchmarks/README.md`](README.md); it is evidence for capacity planning, not a universal latency
guarantee.

## Environment

- Apple M3 Max (arm64), 36 GiB RAM
- macOS Darwin 25.6.0
- .NET SDK 10.0.302, .NET 10 workstation GC
- Release configuration; one scenario per fresh process; no debugger

## Results

| Scenario | Cold compile + render | Cold managed allocation | Cached render | Cached managed allocation | Working set before / after |
| --- | ---: | ---: | ---: | ---: | ---: |
| 5 MiB source | 1,166.9 ms | 303.7 MiB | 4.6 ms | 10.0 MiB | 42.3 / 328.7 MiB |
| 10 MiB source | 1,661.1 ms | 594.8 MiB | 5.3 ms | 20.0 MiB | 42.3 / 479.9 MiB |
| 15 MiB source | 2,037.1 ms | 851.1 MiB | 7.1 ms | 30.0 MiB | 42.3 / 591.6 MiB |
| 1,000 distinct small templates | 6,969.6 ms total | 1,063.5 MiB total | 6.1 ms total | 2.2 MiB total | 42.3 / 241.0 MiB |

The macOS process API returned no peak-working-set counter, so the harness reported `null`/the
original run displayed zero for that field. The before/after working sets and managed-allocation
totals are the usable memory evidence on this host. Timing variance in the very short cached runs
explains why the 10 MiB sample is slower than the 15 MiB sample; the allocation trend is the more
stable scaling signal.

## Evaluation

- All four workloads completed successfully and preserved exact output identity. There was no
  integer overflow, truncation, compiler failure, or cache-key collision at the requested sizes.
- Cold large-template elapsed time and managed allocation scale approximately linearly. Cold work
  allocates about 54-56 times the ASCII source size because Razor parsing, generated C# and Roslyn
  compilation coexist with source and rendered buffers. A 15 MiB input reached about 600 MiB process
  working set on this host, so large cold compilations require an explicit memory budget.
- TASK-040 replaced the `StringWriter`/`StringBuilder` final accumulator with a growable pooled
  character array. Cached string rendering now allocates approximately the UTF-16 result size—10,
  20, and 30 MiB for the three outputs—rather than twice that amount. This is a 50% reduction from
  the original 20.1, 40.1, and 60.2 MiB measurements with no material latency regression.
- The pooled accumulator trades transient allocation for reusable capacity. A cold render must rent
  and populate the accumulator before it creates the immutable result, and the shared pool may retain
  that array for later requests. Used characters are cleared before the array is returned so rendered
  data cannot be observed by a later pool renter. Cold managed-allocation measurements were 4-8%
  higher in these one-shot runs; post-run working set varied in both directions and is not a reliable
  retained-size delta without longer process observation. Applications producing multi-megabyte
  results should still limit concurrency; the `TextWriter` overload remains preferable when no
  result string is required.
- The 1,000-template cold run averaged about 7.35 ms and 1.07 MiB managed allocation per template.
  Cached rerender averaged about 6 microseconds and 2.6 KiB per template. The approximately 199 MiB
  working-set increase is expected because compiled dynamic assemblies and cached descriptors are
  process-lifetime resources; disposing an engine releases caches/watchers but cannot unload
  assemblies loaded into the default load context.

## Stable-tag conclusion

No correctness or super-linear scaling defect was found, and the removable duplicate string
allocation was corrected before 3.0. The remaining results do not justify blocking the tag, but they
do establish operational boundaries: do not accept untrusted templates, cap cold large-template
concurrency, reuse engines and compiled templates, and use a recyclable worker process when a
service continually compiles large numbers of one-off templates. The versioned harness should be
rerun when compiler dependencies, buffering, or assembly-load strategy changes.
